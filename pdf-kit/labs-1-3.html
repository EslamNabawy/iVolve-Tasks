BASICS

The words you need

Nine terms. Everything in these labs is built from them.

TermPlain meaning
Source codeThe .java files a human writes. Cannot be run directly.
CompileTranslate source into bytecode (.class) the computer can execute.
ArtifactThe single finished file a build produces. Here: calculator.jar.
JARA ZIP file of .class files + a manifest. Genuinely all it is.
ManifestA tiny text file inside the JAR. Its Main-Class line says where the program starts.
DependencyA library your code needs. The build tool downloads it for you.
Unit testCode that checks your code — sum(2,3) must equal 5, automatically.
ImageA frozen snapshot: your app + Java runtime + minimal Linux. A template.
ContainerA running copy of an image. One image → many containers.

JDK vs JRE — the distinction Lab 3 is built on

JDKJREWhy you care
Used forBuildingRunningLab 3 Part 1 builds; Part 2 only runs
Compiler✓ included✗ noneA server that only runs an app needs no compiler
Size~180–400 MB~80–180 MBThis gap is the bonus answer
One sentence to remember

A machine that only runs an app does not need a compiler. That is the whole reason one Lab 3 image is three times the size of the other.

THE APP

What you're building

All three labs build the same tiny program — it asks for two numbers and prints four results:

$ java -jar calculator.jar
Enter first number: 10
Enter second number: 5
a = 10.0, b = 5.0
Sum: 15.0      Subtract: 5.0
Multiply: 50.0 Divide: 2.0
The fact that trips everyone up

This app reads from the keyboard. It is not a website — nothing listens on a port. So in Lab 3: (a) EXPOSE 8080 does nothing, it is just a label; (b) you cannot test with curl, you type numbers; (c) you must use docker run -i or it crashes instantly.

LAB 1

Maven — turn source into a JAR

LAB 1·IN: .java source → OUT: target/calculator.jar → this exact file becomes the input to Lab 3
🎯 Goal

Install Java and Maven, then turn the Calculator source code into one runnable file — without compiling anything by hand.

✅ Done when
  • mvn -version reports Java 17
  • mvn test shows Failures: 0, Errors: 0
  • File exists at exactly target/calculator.jar
  • java -jar prints Sum: 15.0, Multiply: 50.0
  • You can explain why java -jar works
Why Maven exists

Without it you would compile by hand, hunt down library files, build a classpath, run tests manually and zip it correctly. Maven does all five from one file — pom.xml — the same way on every machine.

Install Java 17 and Maven
sudo apt update && sudo apt install -y openjdk-17-jdk maven
java -version && mvn -version

The Java version line inside mvn -version must say 17 — that is the one that matters.

Clone the code — outside your repo
mkdir -p ~/labs-workspace
git clone https://github.com/Ibrahim-Adel15/CalculatorMavenApp.git \
  ~/labs-workspace/CalculatorMavenApp

Your submission repo holds your work, not a copy of someone else's source.

Run the unit tests
cd ~/labs-workspace/CalculatorMavenApp && mvn test

Want Tests run: N, Failures: 0, Errors: 0. First run is slow — Maven is downloading libraries into ~/.m2.

Build the artifact
mvn clean package && ls -lh target/calculator.jar

clean deletes old output so you cannot ship a stale build.

Run it and verify
java -jar target/calculator.jar

Type 10 ⏎ 5 ⏎ → expect Sum: 15.0 and Multiply: 50.0.

Prove you understand it — run this
unzip -p target/calculator.jar META-INF/MANIFEST.MF

It prints Main-Class: com.example.calculator.Main. That line is the only reason java -jar works. A JAR is just a ZIP; the manifest tells Java where to start.

LAB 1

Reading pom.xml

Four parts of this file explain everything Maven did — likely exam material.

The four lines that matter
In pom.xmlWhat it isWhy it matters to you
<groupId> <artifactId> <version>CoordinatesThe unique address of your project — a postal address for code. Every library you depend on is named the same way.
<scope>test</scope>Dependency scopeWhy JUnit appeared without you downloading it. test means: used while testing, excluded from the final JAR. Shipping a test framework to production is waste.
<finalName>calculator</finalName>Output nameWhy the file is calculator.jar and not calculator-1.0.0.jar. The lab demands that exact name.
<mainClass>…Main</mainClass>Entry pointWrites the manifest line you printed on the last page. This is what makes the JAR runnable.

The lifecycle — why mvn package also runs your tests

Maven's phases run cumulatively. Naming one runs every phase before it:

validate
check project
→
compile
.java → .class
→
test
run tests
→
package
build .jar
→
install
save locally
The consequence that matters

If a test fails, packaging never happens — Maven refuses to produce a broken artifact. This single behaviour is the foundation of Continuous Integration. Jenkins will later depend on exactly this.

Commands worth memorising
CommandDoesUse it when
mvn cleanDeletes target/Before a build you want to trust
mvn testCompile + run testsChecking your code still works
mvn packageCompile + test + build the JARProducing the deliverable
java -jar f.jarRuns the artifactVerifying the result

LAB 2

Gradle — same job, different tool

LAB 1→LAB 2·IN: the same .java source → OUT: build/libs/calculator.jar · purpose: comparison, not shipping
🎯 Goal

Build the identical app with a second tool, so you can tell what a build tool really does from what is just one tool's style.

✅ Done when
  • gradle -version works (installed via SDKMAN)
  • File exists at build/libs/calculator.jar
  • Output matches Lab 1 exactly
  • Ran gradle build twice → saw UP-TO-DATE, and checked the test count
  • You can name 3 differences from Maven
Mistake on the lab slide

The title says “Go Application with Gradle”, but the repo is Java — the same Calculator.java as Lab 1. Build it as Java and mention the slip in your write-up: noticing it shows you read the code.

Maven vs Gradle — what actually differs
MavenGradleConsequence
Config filepom.xml — XMLbuild.gradle — codeGradle can express logic; Maven cannot
Build commandmvn packagegradle build—
Output foldertarget/build/Different paths in the lab requirements
Repeat builds✗ redoes everything✓ skips unchanged work40 seconds vs 12 minutes on a real codebase
Install Gradle — not with apt
curl -s "https://get.sdkman.io" | bash
source "$HOME/.sdkman/bin/sdkman-init.sh"
sdk install gradle
Clone and build
git clone https://github.com/Ibrahim-Adel15/CalculatorGradleApp.git \
  ~/labs-workspace/CalculatorGradleApp
cd ~/labs-workspace/CalculatorGradleApp && gradle clean build
Run, verify, then build again
java -jar build/libs/calculator.jar
gradle build          # run twice — watch for UP-TO-DATE

Identical output to Lab 1. That's the lesson: the tool changed, the result didn't.

Two traps in one page

1 · Never apt install gradle. Ubuntu ships Gradle 4.4 from 2017; this project needs 6.7+. SDKMAN is how JVM developers really manage these tools.

2 · useJUnitPlatform() is mandatory in build.gradle. Without it Gradle finds zero tests and still reports BUILD SUCCESSFUL. A green build that tested nothing is worse than a red one — nobody investigates it.

Docker — why containers exist

🎯 Goal

Package the app so it runs on any machine that has Docker — no Java required. Build it two different ways and measure why one is far smaller.

✅ Done when
  • Images app1 and app2 both built
  • Both sizes written down before deleting
  • Each container ran and did correct maths
  • whoami prints appuser, not root
  • Containers and images deleted afterwards
  • You can explain the size gap in your own words
❌ Without a container
  • Copy the JAR to the server
  • Hope Java is installed
  • Hope it is the right version
  • Different server → different result
✅ With a container
  • Package app + Java together

Why a non-root user?

By default everything in a container runs as root. If an attacker breaks into your app they are root inside the container — a short step from the host. Creating an ordinary user is two lines and is standard in production. That is why both labs ask for it.

LAB 3 · PART 1

Build inside Docker → app1

Goal of this part: a self-contained build · your machine needs only Docker — no Java, no Maven · Done when: app1 built, size recorded, container verified, both deleted
FROM maven:3.9-eclipse-temurin-17

WORKDIR /app

RUN useradd --create-home appuser

# dependencies first — cached
COPY pom.xml .
RUN mvn -B dependency:go-offline

# source second — changes often
COPY src ./src
RUN mvn -B clean package

RUN chown -R appuser:appuser /app
USER appuser

EXPOSE 8080
ENTRYPOINT ["java","-jar",
  "/app/target/calculator.jar"]
FROM — an official image with Maven and JDK 17 inside. Satisfies "Maven image with Java 17".
WORKDIR — creates /app and works there. Never use RUN cd: each RUN is a new shell, so it doesn't stick.
useradd — creates the non-root user the lab requires.
Why pom.xml alone first? Docker caches each step and discards everything after the first change. Libraries change rarely, your code constantly. Copying pom.xml and downloading libraries first means editing a .java file reuses the cache → 3-minute rebuild becomes 15 seconds.
chown + USER — hand the files over, then drop privileges.
EXPOSE 8080 — a label. Does nothing here. Included because the lab asks.
The trap: where does USER go?

It must come after mvn package. Maven needs to write files — put USER appuser before the build and it fails with permission errors. Put it after and the running app is still unprivileged. You get both.

docker build -f Dockerfile.app1 -t app1 .
docker images app1                       # RECORD THE SIZE
docker run -it --name container1 app1    # type 10 ⏎ 5 ⏎
docker run --rm --entrypoint whoami app1 # must print: appuser
docker rm container1 && docker rmi app1  # container first, then image

Expect roughly 500–800 MB. That whoami line is excellent evidence for your write-up — it proves you met the requirement instead of claiming it.

You must use -i

-i keeps the keyboard connected. Without it the app instantly hits end-of-input and crashes with NoSuchElementException. Run docker run --rm app1 once to see the crash — understanding it beats avoiding it.

LAB 3 · PART 2

Build locally → app2

Goal of this part: the smallest possible image · compile on your machine, copy in only the JAR · Done when: app2 built and its size compared against app1
# on your machine first:
# mvn clean package

FROM eclipse-temurin:17-jre-alpine

WORKDIR /app

RUN adduser -D appuser

COPY --chown=appuser:appuser \
  target/calculator.jar /app/

USER appuser

EXPOSE 8080
ENTRYPOINT ["java","-jar",
  "/app/calculator.jar"]
Two savings in one line.
-jre not -jdk: a runtime with no compiler. We already compiled.
-alpine: a 5 MB Linux instead of a 75 MB one.
adduser, not useradd! Alpine is a different Linux with different commands — useradd gives "command not found". The base image decides which commands exist.
COPY --chown sets ownership while copying, so no extra step is needed.
USER can come earlier now, because there is no build afterwards. Same requirement as Part 1, different answer — that contrast is the lesson.
docker build -f Dockerfile.app2 -t app2 .  &&  docker images app2
BONUS

Why is one 3× bigger?

ImageBaseWhat's insideSize
app1maven + JDK 17JDK + Maven + every downloaded library + source + the JAR~500–800 MB
app2JRE + AlpineJRE + the JAR~200–300 MB
The answer, in one sentence

What you need to BUILD is not what you need to RUN. Compiling needs a compiler, a build tool and every library. Running needs a JVM and one 3.7 KB file. app1 ships the whole workshop; app2 ships only the product.

Size is only the visible symptom
Real costWhy it hurts
SecurityEvery tool in an image is something an attacker can use. A compiler and package manager in production is a gift to them.
SpeedImage size is download time — on every server, on every deployment.
CostYou pay to store and transfer those gigabytes on every build, forever.
But app2 has a real weakness — say this in your write-up

app2 is smaller, yet its build is not reproducible: it depends on your machine having the right Java and the right files in target/. app1 works identically for anyone with Docker. Neither is simply "better" — Part 1 buys reliability, Part 2 buys size. Spotting that trade-off is the point of the lab.

Multi-stage — get both, not either

Not required by the lab. Do it anyway: it is how real projects solve this, and it will lift your grade.

🔨
Stage 1 — build
Full Maven + JDK
produces the JAR
then thrown away
→
🚀
Stage 2 — run
Tiny JRE image
copies in only the JAR
this becomes your image
# ---- stage 1: build ----
FROM maven:3.9-eclipse-temurin-17 AS build
WORKDIR /app
COPY pom.xml .
RUN mvn -B dependency:go-offline
COPY src ./src
RUN mvn -B clean package

# ---- stage 2: run ----
FROM eclipse-temurin:17-jre-alpine
WORKDIR /app
RUN adduser -D appuser
COPY --from=build --chown=appuser:appuser /app/target/calculator.jar /app/
USER appuser
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "/app/calculator.jar"]
How it works

Two FROM lines = two stages. Only the last becomes your image. The magic line is COPY --from=build — it reaches into stage 1 and takes one file. The JDK, Maven, libraries and source are discarded completely.

What actually earns the grade

Anyone can paste commands that worked. Explaining why separates a pass from a strong mark — why a non-root user, why the JRE image is smaller. Write it in your own words; a grader spots copied text instantly.

The one-paragraph summary, if you remember nothing else

Source code cannot run. A build tool (Maven or Gradle) compiles, tests and packages it into one artifact — calculator.jar. That jar still needs Java wherever it goes, so Docker wraps it with its own Java runtime into an image that runs identically anywhere. Labs 1 and 2 are the same step with two tools so you can compare; Lab 3 is the next link. Jenkins later runs the whole chain for you.
