Before any command

You need Linux

Every command here is Linux, and Docker requires a Linux kernel. Windows CMD or PowerShell on their own cannot run any of it.

OptionWho it suitsSetup
WSL2Recommended — what this repo useswsl --install in PowerShell as Administrator, then reboot
Native LinuxA spare machine or dual bootUbuntu 22.04+ / Fedora / Debian
VMKeeping it off your hostVirtualBox, VMware or Hyper-V running Ubuntu

Confirm you are actually inside Linux:

uname -a && head -2 /etc/os-release

Expect Linux and your distribution. On WSL the kernel string also contains microsoft-standard-WSL2.

On WSL, never work under /mnt/c

Keep every project under /home/<you>. Files on the Windows drive cross a filesystem bridge: builds run 5–20× slower, and Linux permissions — the executable bit mvnw and gradlew depend on — are not stored faithfully.

The two-folder rule

~/iVolve-Tasks/      # YOUR work. Committed. Dockerfiles, configs, write-ups.
~/labs-workspace/    # CLONED app source. Never committed.

Your submission should contain what you authored — not a copy of someone else's source, and not build output. .gitignore enforces it.

mkdir -p ~/labs-workspace

Open the repo in VS Code from inside WSL:

code ~/iVolve-Tasks

01

Install the toolchain

Java 17 and Maven

sudo apt update && sudo apt install -y openjdk-17-jdk maven
java -version && mvn -version
CommandWhat it does
apt updateRefreshes the list of available packages. Installs nothing.
openjdk-17-jdkThe full JDK — needed because we compile. The JRE alone is not enough.
-yAuto-confirms prompts.
mvn -versionThe one that matters — shows which JDK Maven will use. Must say 17.

If it reports the wrong JDK, pin it:

echo 'export JAVA_HOME=/usr/lib/jvm/java-17-openjdk-amd64' >> ~/.bashrc && source ~/.bashrc

JAVA_HOME is the variable every JVM tool reads to find the JDK. source re-reads your shell config so it applies now.

Gradle — via SDKMAN, not apt

curl -s "https://get.sdkman.io" | bash && source "$HOME/.sdkman/bin/sdkman-init.sh"
sdk install gradle && gradle -version
Never apt install gradle

Ubuntu ships Gradle 4.4 from 2017; this project needs 6.7+. SDKMAN installs to ~/.sdkman with no sudo, and also manages JDKs — sdk list java.

Docker

CommandWhat it does
docker psLists running containers — the quickest check that the daemon is alive.
sudo service docker startStarts the daemon. WSL has no systemd, so it does not always auto-start.
sudo usermod -aG docker $USERRun docker without sudo. Reopen the terminal after — groups are read at login.

Git and GitHub — one-time setup

Create the repo, then set your identity

cd ~/iVolve-Tasks && git init -b main
cd ~/iVolve-Tasks && git config user.name "Eslam" && git config user.email "you@example.com"
Order matters

git config without --global writes into .git/config, so the repo must exist first. Running it in a plain folder gives fatal: not in a git directory.

ScopeWritten toApplies to
--system/etc/gitconfigEvery user on the machine
--global~/.gitconfigAll your repos
(no flag).git/configThis repo only — highest precedence
 
git config --list --show-origin   # every setting and which file set it

Authenticate

gh auth login

Choose GitHub.com → HTTPS → Yes → Login with a web browser. Copy the one-time code, press Enter, authorize, and wait for the terminal to confirm before touching anything.

CommandWhat it does
gh auth loginAuthenticates the CLI and becomes git's credential helper, so pushes just work.
gh auth statusVerifies the token. Want ✓ Logged in to github.com.
gh auth logout -h github.com -u USERClears a stale entry — needed when hosts.yml has a username but no token, which shows as HTTP 401.

Connect and push

cd ~/iVolve-Tasks && git remote add origin https://github.com/USER/iVolve-Tasks.git
cd ~/iVolve-Tasks && git add . && git commit -m "chore: scaffold labs repo" && git push -u origin main
Do not paste the angle brackets

Placeholders like <username> are markers, not syntax. In bash < means input redirection, so pasting them gives bash: username: No such file or directory.

The per-lab git workflow

If the remote already has a README

GitHub's "Add a README" checkbox creates a commit, so a plain push is rejected. Join the histories rather than force-pushing:

cd ~/iVolve-Tasks && git fetch origin && git merge origin/main --allow-unrelated-histories --no-edit
git checkout --ours README.md && git add README.md && git commit --no-edit
CommandWhat it does
--allow-unrelated-historiesJoins two histories with no common ancestor.
git checkout --ours FILEDuring a conflict, keeps your version. --theirs keeps the remote's.

Every lab ends the same way

cd ~/iVolve-Tasks && git status
# run the line for the lab you just finished
git add "Build Tools/Lab1" && git commit -m "feat(lab1): package with Maven" && git push
git add "Build Tools/Lab2" && git commit -m "feat(lab2): package with Gradle" && git push
git add Docker/Lab3 && git commit -m "feat(lab3): add Dockerfiles" && git push
CommandWhat it does
git status --shortCompact view: M modified, ?? untracked. Run before every commit.
git add "Build Tools/Lab1"Stages one folder. Quotes required — the name has a space.
git add -AStages everything, including deletions.
git diff --stagedShows exactly what is about to be committed.
git log --onelineCompact history.
“nothing to commit” is not an error

Git tracks file changes. Lab commands run in ~/labs-workspace, outside the repo — the write-up in each lab's README is the deliverable. Edit it, then commit.

Lab 1 — Maven

LAB 1 IN .java source → OUT target/calculator.jar → Lab 3 copies this exact file into an image.
git clone https://github.com/Ibrahim-Adel15/CalculatorMavenApp.git ~/labs-workspace/CalculatorMavenApp
cd ~/labs-workspace/CalculatorMavenApp && find . -type f -not -path './.git/*'
cd ~/labs-workspace/CalculatorMavenApp && mvn test
cd ~/labs-workspace/CalculatorMavenApp && mvn clean package && ls -lh target/calculator.jar
java -jar ~/labs-workspace/CalculatorMavenApp/target/calculator.jar
CommandWhat it does
find . -type f -not -path './.git/*'Lists every real file, hiding git internals. Four files here.
mvn testCompiles, then runs tests. Want Tests run: N, Failures: 0, Errors: 0.
mvn cleanDeletes target/ so you cannot ship a stale build.
mvn packageRuns validate → compile → test → package. A failed test stops it.
ls -lhHuman-readable sizes — expect about 3.7K.
java -jar FILERuns the artifact. Type 10, Enter, 5, Enter.

Verify without typing — how CI does it

printf '10\n5\n' | java -jar ~/labs-workspace/CalculatorMavenApp/target/calculator.jar

printf writes to stdout, | pipes it into the program's stdin, \n is the Enter key. Exactly what docker run -i provides — and what its absence removes.

Prove why java -jar works

unzip -p ~/labs-workspace/CalculatorMavenApp/target/calculator.jar META-INF/MANIFEST.MF

unzip -p prints one file from the archive to stdout — proving a JAR is a ZIP. It shows Main-Class: com.example.calculator.Main, the only reason the JAR is runnable.

cd ~/iVolve-Tasks && git add "Build Tools/Lab1" && git commit -m "feat(lab1): Maven" && git push

Lab 3 — Docker

LAB 3 IN target/calculator.jar from Lab 1 → OUT images app1 and app2 → later run by Kubernetes.

Part 1 — build inside Docker

cd ~/labs-workspace/CalculatorMavenApp && docker build -f Dockerfile.app1 -t app1 .
docker images app1                        # RECORD THE SIZE — the bonus needs it
docker run -it --name container1 app1     # then type 10, Enter, 5, Enter
docker run --rm --entrypoint whoami app1  # must print: appuser
docker rm container1 && docker rmi app1   # container first, then image
Command / flagWhat it does
docker build -f F -t N .-f picks the Dockerfile, -t tags it, and . is the build context — the folder sent to the daemon, which COPY reads from.
-iKeeps stdin open. Mandatory — without it the app crashes with NoSuchElementException.
-tAllocates a terminal so prompts render.
--rmDeletes the container when it exits.
--entrypoint CMDOverrides the image's entrypoint for a one-off command — a useful debugging trick.
docker rmiDeletes an image. The container must go first.
docker history IMGShows each layer and its size — reveals where the megabytes went.

Expect ~500–800 MB.

Part 2 — build locally

cd ~/labs-workspace/CalculatorMavenApp && mvn clean package
printf 'src/\n.git/\ntarget/*\n!target/calculator.jar\nDockerfile*\n' > .dockerignore
docker build -f Dockerfile.app2 -t app2 . && docker images app2
docker run -it --name container2 app2
docker rm container2 && docker rmi app2

.dockerignore excludes files from the build context, like .gitignore. !target/calculator.jar re-includes one file after excluding its folder — later rules win. Expect ~200–300 MB.

CI/CD — read this first

A pipeline needs source code. This repo has none.

~/iVolve-Tasks holds write-ups and Dockerfiles — no pom.xml, no .java. A workflow added here would run, find nothing to compile and fail, leaving a red ✗ for your instructor. The pipeline belongs in the application repo.

So fork the app first — everything in the next section goes in that repo:

GitHub Actions — build, test, publish

The commands from Labs 1–3, run automatically on a clean machine at every push.

Create .github/workflows/ci.yml in the forked app repo:

name: CI
on:
  push:
    branches: [ main ]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          java-version: '17'
          distribution: 'temurin'
          cache: maven
      - run: mvn -B test
      - run: mvn -B clean package
      - uses: actions/upload-artifact@v4
        with:
          name: calculator-jar
          path: target/calculator.jar
LineWhat it does
on: pushTriggers the pipeline on every push to main.
runs-on: ubuntu-latestGitHub gives you a fresh Ubuntu VM per run.
actions/checkout@v4Clones your repo into that VM. Nothing exists until you do this.
cache: mavenCaches ~/.m2, so later runs skip re-downloading.
mvn -B testLab 1, automated. -B = batch mode, no progress spam in logs.
upload-artifactSaves the JAR so you can download it from the run page.
 
git add .github/workflows/ci.yml && git commit -m "ci: build and test with Maven" && git push
gh run list --limit 5     # recent runs and their status
gh run watch              # follow the current run live
gh run view --log-failed  # logs for only the failed steps
This is the whole idea of CI

If it passes on a fresh VM that has nothing installed, it is not “works on my machine” any more.

CD — publish the image

Append this job to the same file. It builds Lab 3's image and pushes it to GitHub's own registry, which needs no extra account or secret.

  docker:
    needs: build
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
    steps:
      - uses: actions/checkout@v4
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - uses: docker/build-push-action@v6
        with:
          context: .
          file: ./Dockerfile.multistage
          push: true
          tags: |
            ghcr.io/${{ github.repository_owner }}/calculator:latest
            ghcr.io/${{ github.repository_owner }}/calculator:${{ github.sha }}
LineWhat it does
needs: buildThe gate. Skipped unless tests passed — a broken image is never published.
secrets.GITHUB_TOKENProvided automatically. Nothing to create.
file: Dockerfile.multistageUses your Lab 3 bonus Dockerfile — small and reproducible.
two tags:latest for convenience, :${{ github.sha }} pins the exact commit. Always tag the commit — latest makes rollback guesswork.

Doing it by hand — what the pipeline automates

echo $GITHUB_TOKEN | docker login ghcr.io -u USER --password-stdin
docker build -f Dockerfile.multistage -t ghcr.io/user/calculator:latest .
docker push ghcr.io/user/calculator:latest

--password-stdin keeps the token out of your shell history. For Docker Hub instead, store credentials with gh secret set DOCKERHUB_TOKEN — never put them in the YAML.

Jenkins & cheat sheet

Jenkins expresses the identical chain in a Jenkinsfile committed beside your code:

pipeline {
    agent any
    stages {
        stage('Test')  { steps { sh 'mvn -B test' } }
        stage('Build') { steps { sh 'mvn -B clean package' } }
        stage('Image') { steps { sh 'docker build -t calculator:$BUILD_NUMBER .' } }
    }
    post { always { junit 'target/surefire-reports/*.xml' } }
}

Same order as Labs 1 → 3. $BUILD_NUMBER increments per run — the same idea as tagging with the git SHA. Actions is hosted and free for public repos; Jenkins you run yourself but integrates with anything. The pipeline logic is identical; only the syntax differs.
